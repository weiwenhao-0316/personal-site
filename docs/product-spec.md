# haoriver.site 产品定义草案

> 状态：草案，尚未冻结
> 创建时间：2026-08-30
> 用途：帮助用户和 AI 在继续开发前收敛需求，避免功能不断扩张。

## 1. 一句话定位

`haoriver.site` 是一个以学习和个人使用为主的数字收纳空间：把外部收藏、学习笔记、资料和项目记录整理成自己的内容资产，并逐步形成“输入、整理、输出”的闭环。

## 2. 产品属性

当前采用双重定位，但优先级不同：

1. **第一优先级：个人生产和学习工具**

   用户可以用它保存内容、记录学习过程、练习真实的软件工程开发。

2. **第二优先级：对外展示的个人作品**

   未来可以给同学、老师、雇主或面试官展示，但不能为了展示效果过早堆叠复杂功能。

## 3. 要解决的问题

当前最核心的问题不是“页面不够多”，而是内容进入网站后缺少稳定的流动路径：

```text
外部链接 / 文件
        ↓
临时收纳
        ↓
分类和补充批注
        ↓
笔记、资料或项目记录
        ↓
形成可以回看的个人内容
```

## 4. 第一阶段产品目标

第一阶段只追求一个稳定的个人版本：

- 可以保存和管理收藏；
- 可以保存和管理笔记；
- 可以把临时收纳的内容转成笔记或收藏；
- 刷新页面后数据不会因为浏览器页面关闭而消失；
- 用户能清楚知道哪些功能已经完成、哪些还只是规划；
- 每次改动都有明确的验证方式。

这里的“闭环”先指内容流程闭环，不要求所有模块第一天都完成云端同步。Library、Vault 和 Wallpaper 可以暂时保留本地存储，但必须在界面和文档中明确说明这一点。

## 5. 第一阶段范围

### 必须保留

| 模块 | 第一阶段职责 | 当前状态 |
|---|---|---|
| Home | 作为入口，展示真实的最近更新和当前阶段 | 部分完成，内容是静态配置 |
| Collection | 保存外部链接、分类、标签、批注和状态 | MySQL CRUD 代码已完成 |
| Notes | 保存学习记录、复盘和整理结果 | MySQL CRUD 代码已完成 |
| Vault | 临时收纳链接和文件，并支持转存 | 浏览器 IndexedDB，暂时保留 |
| Library | 保存可复用资料 | 浏览器 localStorage，暂时保留 |
| Projects | 展示正在建设的项目 | 暂时使用静态内容 |
| Chat | 提供基础 AI 对话实验 | 暂时只做普通聊天 |

### 第一阶段暂不追求

- 多用户和复杂账号体系；
- 完整 JWT 登录系统；
- AI 自动摘要、自动分类和批量处理；
- 文件服务器、对象存储和大文件上传；
- Projects 动态后台；
- 复杂搜索、推荐、统计和标签管理；
- 微服务、Docker 或过度抽象的后端架构。

这些不是永远不做，而是不能在核心闭环尚未稳定前抢占开发重点。

## 6. 页面职责

| 页面 | 用户要完成的事情 | 不应该承担的事情 |
|---|---|---|
| Home | 了解项目是什么、当前做到哪一步、从哪里开始 | 承载全部业务数据 |
| Collection | 快速保存和整理外部内容 | 取代笔记正文编辑 |
| Notes | 把内容变成自己的记录和判断 | 作为任意文件仓库 |
| Library | 长期保存和复用资料 | 在第一阶段承担完整云盘能力 |
| Vault | 临时收纳和转存 | 作为最终归档位置 |
| Projects | 展示真实项目成果 | 变成项目管理系统 |
| Chat | 做 AI 能力实验 | 在没有边界时自动修改业务数据 |

## 7. 第一阶段完成标准

满足以下条件，才算第一阶段闭环完成：

1. Collection 页面可以读取、新增、编辑和删除收藏。
2. Notes 页面可以读取、新增、编辑和删除笔记。
3. Collection 和 Notes 的数据来源、字段和错误处理已经核对清楚。
4. Vault 至少可以在当前浏览器完成链接或文件的临时收纳。
5. Vault 转存到 Notes 或 Collection 时，成功和失败状态都能正确反馈。
6. 关键数据的保存位置在页面和文档中明确写出。
7. 前端构建通过，后端可以在干净环境启动。
8. 线上部署状态经过用户确认，而不是只根据代码推断。

## 8. 当前待确认的产品问题

这些问题会影响后续设计，暂时不让 AI 擅自决定：

| 问题 | 当前暂定答案 | 后续需要确认的内容 |
|---|---|---|
| 网站主要给谁使用 | 主要给自己，兼顾展示 | 是否允许其他人查看或操作 |
| 数据是否都必须跨设备同步 | 核心内容最终需要，第一阶段分步完成 | Library/Vault 是否必须马上上云 |
| Vault 和 Collection 的关系 | Vault 是临时收纳，Collection 是长期链接收藏 | 是否需要自动去重、转存后删除原件 |
| Notes 的写作形式 | 先用纯文本，保留简单可靠 | 什么时候引入 Markdown |
| AI 的职责 | 先聊天，后续做内容整理 | 是否允许 AI 直接写入数据库 |
| Projects 是否需要后台管理 | 第一阶段不需要 | 什么时候从静态展示变成动态数据 |

## 9. 需求变更规则

以后产生新想法时，不直接进入代码。先把它归入下面一种：

- **核心闭环**：不完成就无法使用主流程；
- **体验优化**：已有功能更好用，但不改变核心模型；
- **未来能力**：当前不影响使用，可以排期；
- **暂不处理**：想法有价值，但现在会扩大范围或引入高风险。

只有“核心闭环”任务可以打断当前主线。其他想法先记录到路线图，不立即开发。

## 10. 一张任务卡应该包含什么

每次交给 AI 的任务至少写清楚：

```text
任务名称：
所属阶段：
要解决的问题：
期望结果：
允许修改的文件：
明确不修改的内容：
完成标准：
验证命令或人工验收步骤：
是否允许部署：否，除非用户明确授权
完成后需要更新的文档：
```

AI 必须先检查现状，再给出短计划；实现后必须报告实际修改、验证结果和未验证事项。不能只因为代码写完，就把任务标为完成。

## 11. 当前产品结论

当前不需要继续增加页面。下一阶段应先完成：

1. 确认 Notes 已经在线生效；
2. 确认第一阶段闭环的验收结果；
3. 根据用户选择，决定是先做文档规范、错误处理，还是开始 Library 上云；
4. 任何新的复杂功能先记录，不立即实现。

本文件是产品讨论的起点，不是不可修改的最终答案。用户确认后，才把暂定内容升级为正式需求。
